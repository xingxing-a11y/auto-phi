# 换一台设备（端内 APK 版）

> 适用对象：`android/play` 打出来的那个 APK —— 端内自己点 ▶、自己听曲首起音定零点。
> 一句话：换机只需重测三个跟设备走的量（`c` / 落点 / 手势区），其余照旧。
> ⛔ 本文不靠 PC 时代的 `L` / `e` / `D` / `G` 做标定：端内零点由 onset 自听得出，那四个量不再参与。

---

## 0. 哪些参数跟设备走，哪些跟曲子走

| 参数 | 含义 | 跟谁走 | 换机要不要重测 |
|---|---|---|---|
| `c` | 这台设备「读到播放流」比「实际发声」晚多少 ms | 设备（出厂 177） | 要，约 6 轮 / 15 分钟 |
| 落点（学到的坐标） | 右下角「开始演奏」在屏幕上的位置 | 设备 × 分辨率 | 要（点一次，1 分钟）；旧值会自动失效 |
| `GESTURE_TOP/BOTTOM/SIDE_REL` | 系统手势区宽度（屏幕比例） | 设备 × 分辨率 | 一般不用；只在贴边音符会被拉通知栏时改代码 |
| `fit` | 画布 → 屏幕的映射方式（现固定 `height`） | 宽高比 | 只在宽高比变化时才可能要改代码 |
| `K` | 该曲「闸门认定的起音」与「母带真实起点」的差（ms） | 曲子 | 不用，可跨设备继承 |
| `sil_ref` / `sil_thr` / 包络指纹 | 母带静音长度、起音阈值、前 30 s 指纹 | 曲子（打包时生成） | 不用 |
| 谱面与 payload | 1920×1080 画布上的事件表 | 不含任何设备信息 | 不用 |

两条最容易搞反的：

- 端内用的是 `L_dev = K + c`。`K` 是曲子的账，`c` 是设备的账 ⇒ 换机后只改 `c`，别去动 `K`（那等于把设备的偏差记到某首曲子头上）。
- 课题模式的 `trim` 不是设备参数。它是代码里一张按曲的绝对值表（`COURSE_TRIM_BY_KEY`），且只作用于课题模式，单曲模式完全不读它。

## 1. 换机按这个顺序做

### 1.1 `c`：每台设备一次（约 6 轮 / 15 分钟）

App 帮助页 §② 第 5 步写的就是这套，这里只补判据：

1. 第一轮 `c` 不动（保持出厂 177）。这一轮会顺带自动测出该曲的 `K`，之后不用再管 `K`；
2. 之后每轮只改 `c`，一次 ±20：全 Perfect ⇒ 对了；一堆 Late ⇒ 加大；一堆 Early ⇒ 减小；
3. 想更准就找两个端点 ——「最后一次还出 Late」和「第一次开始出 Early」—— 两端取中点，精度约 ±10 ms；
4. 填回中点，再打一轮确认。

拿什么当尺子：Cthugha IN（1333 音符、并发 4、无起音盲区、约 156 s）或 Bounded Quietude IN（1286 音符、并发 4、无盲区、约 152 s）。改法：首页顶部 `c=…` 小字点开填，下一轮生效。

> ⚠ 曲库是游戏资产的全量谱面，不代表你账号已解锁 —— 游戏里没有的曲子打不了。

### 1.2 落点：点一次就学会（1 分钟）

点顶部 `▶ 落点 x,y` → 「学习落点」→ 切回游戏停在选曲页 → 等提示「现在开始监听」→ 点一下「开始演奏」。

判据只有一条：之后按「测试 ▶」，游戏有没有开始加载。判读行（`✓ 在框内` / `⚠ 贴边` / `✗ 出界`）只是参考，不是结论。
完整流程与四种失败情形见 [`start-button-calibration.md`](start-button-calibration.md)。

### 1.3 手势区：只在贴边音符出事时改

症状：音符贴着屏幕顶边/底边时，通知栏被拉下来、或游戏被踢回桌面 —— 系统把手势抢走了。

1. 实测边界：从四边内侧不同距离下滑 / 横划，找「系统开始接管」的那条线。
   HONOR ALT-AN00（1610×720）实测：顶 `y≤74`、底 `y≥640`、左 `x≤104`、右 `x≥1580`；
2. 改的比例：`android/injector/.../sched/Scheduler.java` 的 `GESTURE_TOP_REL` / `GESTURE_BOTTOM_REL` / `GESTURE_SIDE_REL`
   （现值 `92/720`、`92/720`、`12/1610`），改完重打包；
3. 必须过自检：`bash android/play/selftest.sh` —— `GestureClampSelfTest` 钉住四个数：
   顶部 `92`、底部 `628`、最左 `12`、最右 `1598`（1610×720 上）。

> ⛔ 别拿实测边界反推比例，两个方向的理由不同：
> 顶 / 底现值 92 px，比实测内缩（74 / 80）多留了 18 px 余量，按实测改会偷偷削掉这层保护；
> 侧边现值 12 px 反而小于实测的 30 px（已知不完美，见 §5），但同样不能随手改成 30 —— 自检会红，那是有意的决定。
> ⛔ 只有按下点被夹，MOVE 保持真实轨迹 —— 全夹会把贴边的滑动轨迹压平，变成一堆 Good / Miss。

### 1.4 `fit` 与画布：只在宽高比变了才要碰

端内固定 `fit=height`，映射分两步，公式都写在 `Scheduler` 里：

```
① 载荷坐标 → canvas：k = srcW/canvasW，yOff = (srcH − canvasH×k)/2
② canvas → 设备：    k = dstH/canvasH，xOff = (dstW − canvasW×k)/2     （fit=height）
```

载荷里有两个尺寸字段，别搞混：`canvas`（游戏渲染画布，1920×1080，坐标基准）与 `screen`（打包时的虚拟屏，
1080×2340，只是第 ① 步的中间层）。历史事故是有人把 `screen` 的值填进了 `canvas` 字段 —— 事件一条不少地发出去，成绩却是 40%。

1610×720 上算出来是：两侧黑边各 165，内容区 1280×720，判定线在 `y = 360`（= `dstH / 2`）。

每次开跑日志都会打一行 `载荷口径 canvas=… screen=…`，这是换机时最该先看的东西。
如果整轮成绩是系统性偏移（不是抖动）、宽高比又明显不是 2.24，先怀疑 `fit`；
日志里那行 `显示 1610x720（横屏口径，fit=height）` 会告诉你它按哪种口径算的。

## 2. 这些不用动，别白忙

| 东西 | 为什么不用动 |
|---|---|
| `K` | 曲子的属性，跟着谱面走。换机后第 1 轮会自动重测一次，也可以直接沿用 |
| `assets/` 里的谱面与 payload | 全是曲谱结构量，不含任何设备信息 |
| 曲库门槛（`margin ≥ 0.342`，全库 770 条） | 由算法延迟算出，与设备无关 ⇒ 这批换机后直接能打 |
| PC 侧的逐曲 `G` 缓存 | 带设备序列号，不可移植；端内这条路根本不读它 |

⚠ Ⅱ 类曲目（有起音盲区）换机后要先打一轮把 `lead` 学出来，第 2 轮起才能预派 —— 这是曲子属性，与设备无关。

## 3. 验收顺序（从便宜到贵，每步不过就停）

| # | 步骤 | 成本 | 判据 |
|---|---|---|---|
| 1 | `bash android/play/selftest.sh` | 1 分钟 | exit 0，全绿 |
| 2 | App 顶部看 `▶ 落点 x,y`；开跑后日志里看 `▶ 位置 …` 与判读行 | 0 | 来源对（学到的 / 出厂）；判读不是 `✗ 出界` |
| 3 | 单曲跑一轮（onset 零点） | 2~3 分钟 | 日志出现「已点 ▶」「曲首 onset：点击后 +…」「零点 = onset …」；结算全 P，或 Good ≤3 |
| 4 | 同一首再跑一轮 | 2~3 分钟 | Good 数稳定（不是这轮 1、下轮 100）⇒ 这台设备没有大抖动 |
| 5 | 课题模式三首 | 约 8 分钟 | 三份 trace 都落盘；看结算 Early / Late 的方向决定下一步 |

第 5 步之后往哪走：

- 全 Late ⇒ `c` 还小，回 1.1（⛔ 别去调 `trim`，那不是旋钮）；
- 全 Early ⇒ `c` 大了，回 1.1；
- 两向都很少，只有零星 Good ⇒ 这就正常了 —— 判定是概率事件，σ ≈ 24 ms。

## 4. 故障对照表（看日志最后几行就能定位）

| 日志 | 病因 | 处置 |
|---|---|---|
| `没听到曲首的琴声` | 8 秒倒计时内没切回游戏，那一下 ▶ 点空了（最常见） | 重打；反复出现就先做 1.2 |
| `录屏被系统中断了` | 录屏授权没生效，或被别的录屏/投屏抢走 | 重新点「开始演奏」并允许录屏 |
| `▶ 落点 ✗ 出界` / `⚠ 贴边` | 落点不在按钮上 | 1.2 用「学习落点」重记 |
| `Shizuku 门禁未过` | 没授权，或重装后授权丢了 | 回帮助页 §② 第 3 步重新授权 |
| `上一轮还没收尾` | 上一轮的播放线程还活着（`worker.isAlive()`；代码里没有等待或超时机制，直接拒绝本次点击） | 等它跑完再点，别连点 |
| `这首的谱面数据是空的` | assets 有问题 | 别硬打；先怀疑画布尺寸是不是 1920×1080 |
| `载荷 canvas 口径不对：…（宽高比 … ≠ 16:9）` | `canvas` 字段被填成了 `screen` 的值 | 重出 assets；这不是时基问题，调 `c` 没用 |
| `零点偏早 … ⇒ 前 X s 的音符会被跳过` | 起音认早了（正常应 ≈ `sil_ref`） | 看前一行「曲首 onset：点击后 +… ms」；反复偏早查环境噪声 |
| `没有 Shizuku 注入代理` | 绑定失败 | 重启 App；确认 Shizuku 在跑 |
| 结算全 Late / 全 Early | `c` 偏小 / 偏大（课题模式下也先查这个） | 回 1.1 |

## 5. 已知不完美（不是 bug，别硬刚）

1. 侧边只留 12/1610（约 0.75%），窄于某些机型的手势区。之所以没出事，是 `fit=height` 的黑边把音符隔开了；
   宽高比接近 16:9 的机器黑边很窄，侧边手势区会压到音符上 —— 换机后只在横滑（Drag / Flick）时丢触摸，先怀疑这里。
2. 落点判读框是「一台机器实测反推」的矩形，不是物理真值：超出不代表一定点不中，落在中心也不等于一定点中。
   唯一能定论的只有「点完游戏有没有开始加载」。
3. 课题模式的 `trim` 编在 APK 里，用户改不了。换机后如果只有课题模式偏、单曲正常，先回 1.1 把 `c` 确认掉，
   别指望调 `trim`（历史上有三次把它调大，结果 Good 变多）。
4. rezero 与盲区预派都有代码但默认关闭，理由写在代码注释里（实测都比关闭更差）。换机不是打开它们的理由。
